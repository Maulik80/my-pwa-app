## 1. Project Overview

**SKPT Cricket** is a mobile-first Progressive Web Application (PWA) demo for managing cricket tournaments, live scoring, and match viewing. The app is **mobile-first** and optimized for Phone and Tablet. Desktop is supported for responsive admin/super-admin use where practical; the primary scorer experience remains mobile-first.

> **Note:** This is a **demo project** — no real database. All data is mock/static. Authentication is simulated with hardcoded credentials.

### Key Characteristics

| Attribute | Value |
|-----------|-------|
| **Type** | Progressive Web App (PWA) — Demo |
| **Target Devices** | Phone & Tablet primary; responsive tablet/desktop admin support |
| **Theme** | Blue + White |
| **Backend** | None — intentionally deferred; local demo persistence only |
| **Auth** | Simulated demo authentication; not production security |
| **Deployment** | Vercel |
| **Offline Support** | Offline-first demo mode — Service Worker + IndexedDB |
| **Installable** | Yes — where browser/platform supports PWA installation |

## 5. Architecture Flow

The current project is a **frontend-only PWA demo**. It must work without a backend while keeping clear boundaries for a future API/synchronization layer.

```text
┌─────────────────────────────────────────────────────────────┐
│                         PAGE                                │
│              Composition / route-level UI                   │
└──────────────────────────────┬──────────────────────────────┘
                               │
┌──────────────────────────────▼──────────────────────────────┐
│                      COMPONENTS                             │
│             Reusable UI + user interactions                 │
└──────────────────────────────┬──────────────────────────────┘
                               │
┌──────────────────────────────▼──────────────────────────────┐
│                       ZUSTAND                               │
│          UI / session / scoring application state            │
└──────────────────────────────┬──────────────────────────────┘
                               │
                    ┌──────────▼──────────┐
                    │   Persistence Layer │
                    │                     │
                    │  IndexedDB          │
                    │  localStorage       │
                    └──────────┬──────────┘
                               │
             ┌─────────────────▼─────────────────┐
             │          PWA SERVICE WORKER       │
             │                                   │
             │ App Shell / Static Assets         │
             │ Navigation Fallback               │
             │ Runtime Caching                   │
             │ Update Lifecycle                  │
             └───────────────────────────────────┘
```

### Offline-First Demo Flow

```text
User opens SKPT Cricket
        │
        ▼
Service Worker loads application shell
        │
        ▼
React application starts
        │
        ▼
Load demo data / persisted local data
        │
        ▼
User performs actions
        │
        ▼
Zustand updates application state
        │
        ▼
Important demo data is persisted locally
        │
        ├──────── ONLINE ────────┐
        │                        │
        └────── OFFLINE          │
                 │               │
                 ▼               │
        Continue using app       │
        without network          │
                 │               │
                 └───────┬───────┘
                         ▼
                 Data remains local
```

### Future Backend Boundary

The current phase intentionally has **no backend**.

The persistence layer must therefore be designed so that a future phase can introduce:

```text
IndexedDB
    │
    ▼
Sync Queue
    │
    ▼
Future API
    │
    ▼
Future Database
    │
    ▼
Future WebSocket / SSE
```

Do not implement the backend in the current phase.

### Data Flow Rules

| Rule | Description |
|------|-------------|
| **Pages** | Compose page-level UI; avoid business/data-access logic |
| **Components** | Render UI and emit user actions |
| **Zustand** | Manage application/UI/session/scoring state |
| **Persistence Layer** | Persist important demo data and scoring state locally |
| **IndexedDB** | Store structured/offline application data |
| **localStorage** | Store small preferences such as dismissed install UI |
| **Service Worker** | Cache application resources and provide offline navigation |
| **Mock Data** | Seed initial demo data |
| **No API** | No backend/API calls in the current phase |
| **Future Sync** | Keep persistence boundaries ready for later synchronization |

## 6. PWA Configuration

SKPT Cricket is implemented as an **offline-capable, installable Progressive Web Application**.

### PWA Goals

The current frontend phase must provide:

- Installable application experience
- Standalone display mode
- Valid web app manifest
- 192px and 512px application icons
- Maskable icons
- Service worker
- Offline application shell
- Offline SPA navigation
- Persistent local demo/scoring data
- Online/offline status
- Install prompt where supported
- Safe service-worker update handling
- Cache cleanup
- Vercel SPA routing
- Mobile-first interaction

### Service Worker Strategy

| Resource Type | Strategy | Purpose |
|---------------|----------|---------|
| App Shell | Precache / Cache First | Start the application offline |
| JS/CSS/Fonts | Precache | Fast repeat launches |
| Local Icons | Precache | Install/app-shell assets |
| Local Images | Cache First / appropriate runtime cache | Reuse static imagery |
| External Images | Stale While Revalidate only where required | Avoid unnecessary network dependency |
| SPA Navigation | Navigation Fallback | Allow React Router routes offline |
| Future API Data | Not implemented in current phase | Reserved for future backend |

Do not blindly cache every network request.

The generated manifest must contain:


```text

    ├── icon-512.png

    └── icon-maskable-512.png
```

These files must actually exist. Manifest references must never point to missing assets.

### Install Prompt

`InstallPrompt.tsx` and `usePWAInstall.ts` must provide one consistent installation flow.

Requirements:

- Detect `beforeinstallprompt`
- Store the deferred installation event
- Show a custom install CTA when appropriate
- Allow dismissal
- Persist dismissal locally
- Hide install CTA when already installed
- Do not show a broken CTA when the browser does not expose the install event
- Detect standalone/installed mode
- Avoid repeatedly interrupting the user

### Service Worker Updates

Use `vite-plugin-pwa` update handling.

When a new version is available:

```text
┌─────────────────────────────────┐
│ New version available           │
│                                 │
│ Update SKPT Cricket?            │
│                                 │
│          [ Update ]             │
└─────────────────────────────────┘
```

The update flow must avoid infinite reload loops and should not unexpectedly destroy the active UI.

### Network Status

`NetworkStatus.tsx` and `useNetworkStatus.ts` provide application-level connectivity awareness.

Offline message:

```text
Offline Mode
Your local demo data is being saved on this device.
```

Online recovery message:

```text
Back Online
Your local demo data remains available.
```

Messages must be non-blocking and accessible.

### IndexedDB Persistence

IndexedDB is used for structured local demo data.

Recommended stores:

```text
matches
teams
players
tournaments
scoringEvents
preferences
syncQueue
```

The exact implementation may use an IndexedDB helper library such as `idb`.

Do not access IndexedDB directly from every component. Keep database operations inside a dedicated persistence layer.

### Scoring Persistence

Live scoring is demo-only but must survive refresh/offline use.

Persist important state such as:

- Current match
- Current innings
- Current over
- Ball history
- Score
- Wickets
- Batter state
- Bowler state
- Match status

A scorer refreshing the page must not lose locally persisted demo scoring data.

### Event-Oriented Scoring Data

Scoring data should be representable as individual events:

```typescript
interface ScoringEvent {
  id: string;
  matchId: string;
  inningsId: string;
  over: number;
  ball: number;
  runs: number;
  extras?: number;
  wicket?: boolean;
  timestamp: string;
  syncStatus: 'local' | 'pending' | 'synced';
}
```

`syncStatus` is local metadata for future synchronization. No real synchronization is implemented in this phase.

### Future Sync Queue

A local `syncQueue` may be maintained for future backend integration.

Current behavior:

```text
Local change
    ↓
Persist locally
    ↓
Mark as local/pending
    ↓
No backend request
```

Future behavior:

```text
Local change
    ↓
IndexedDB
    ↓
Sync Queue
    ↓
API
    ↓
Database
```

The current project must **not** create fake API calls.

### Offline Requirements

When DevTools is switched to Offline, the production build should still allow:

- App startup
- React Router navigation
- Opening cached/demo pages
- Viewing local tournament data
- Viewing local team data
- Viewing local match data
- Using demo scoring
- Persisting scoring changes
- Refreshing the page without losing persisted local data

## 9. State Management

### Zustand Stores

Zustand remains the primary in-memory application state layer.

#### `useAuthStore`

```typescript
interface AuthState {
  user: User | null;
  role: 'super_admin' | 'admin' | 'viewer' | null;
  isAuthenticated: boolean;
  isLoading: boolean;
  login: (email: string, password: string) => Promise<boolean>;
  loginAsAdmin: () => void;
  loginAsSuperAdmin: () => void;
  logout: () => void;
}
```

Authentication is simulated for the demo and is **not a security boundary**.

#### `useUIStore`

```typescript
interface UIState {
  sidebarOpen: boolean;
  activeModal: string | null;
  toasts: Toast[];
  toggleSidebar: () => void;
  openModal: (id: string) => void;
  closeModal: () => void;
  addToast: (toast: Toast) => void;
  removeToast: (id: string) => void;
}
```

#### `useScoringStore`

```typescript
interface ScoringState {
  currentMatch: Match | null;
  currentInnings: Innings | null;
  currentOver: Ball[];
  currentBatsman: Batsman | null;
  currentBowler: Bowler | null;
  isScoring: boolean;
  actions: { ... };
}
```

Important scoring state must be persisted through the local persistence layer so refresh/offline use does not destroy the demo session.

#### `useNetworkStore`

Stores the current connectivity state:

```text
online
offline
```

This state is used by the network status UI and offline-aware application behavior.

### PWA Hooks

Recommended hooks:

| Hook | Purpose |
|------|---------|
| `usePWAInstall` | Installation prompt lifecycle |
| `usePWAUpdate` | Service-worker update lifecycle |
| `useNetworkStatus` | Browser online/offline state |
| `useLiveMatch` | Demo live-match data |
| `useCountdown` | Match/tournament countdowns |

### Persistence Layer

Recommended structure:

```text
src/lib/pwa/
├── db.ts
├── storage.ts
├── syncQueue.ts
└── types.ts
```

Responsibilities:

- `db.ts` — IndexedDB initialization and stores
- `storage.ts` — persistence/read/write helpers
- `syncQueue.ts` — future synchronization queue abstraction
- `types.ts` — persistence-specific types

The UI must not directly manipulate IndexedDB transactions.

```json
      ]
    }
  ]
```

### PWA Deployment Requirements

Before deployment, verify:

1. `npm run build` succeeds.
2. The production preview loads correctly.
3. The generated service worker exists.
4. The manifest is available and valid.
5. All referenced PWA icons exist.
6. React Router routes work after direct navigation.
7. Offline mode works against the production build.
8. Local scoring data survives a page refresh.
9. Service-worker updates do not cause reload loops.
10. Vercel SPA fallback remains enabled.

### Cache Headers

Static hashed assets may use long-lived immutable caching.

The service worker itself must remain updateable and should not be given an immutable cache policy.

The existing `vercel.json` should therefore preserve a no-cache policy for the generated service-worker entry point where applicable.
